**core:** a remote server can declare a peer identity in the configuration file: `tls.peer_identity` with a `key_ref` naming the key lineage, and `spki_sha256` listing the key pins it may present (ADR-030). A key pin is `sha256:` followed by 64 lowercase hex characters: the SHA-256 of the DER SubjectPublicKeyInfo. Every connection to such a server must end at a listed key, and this is checked inside the TLS 1.3 handshake before any request byte is written. A refusal is a `deny` with reason `upstream_peer_key_mismatch`. The server's upstream identity becomes `peer-key:<key_ref>`, so its digest pins survive an address change and a key rotation. These declarations are refused at load: a peer identity on a mode other than `remote`, on an `http://` endpoint, with `verify_ssl: false`, with an empty or non-canonical key list, or with no `key_ref`. A `ca_cert_path` alongside a peer identity is ignored, with a warning. This release reads the declaration from the configuration file only; the REST API and the operator cannot declare one yet. `tls.max_connection_age` and `peer_identity.issuance` are refused at load until a later release implements them.
