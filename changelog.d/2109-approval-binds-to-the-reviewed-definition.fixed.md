**core:** A discovery approval can now be bound to the definition the operator reviewed. `hangar_discovered`, `hangar_quarantine`, `GET /api/discovery/pending` and `GET /api/discovery/quarantined` list a `definition_digest`, the full SHA-256 of the definition (connection, metadata, mode and source); `hangar_approve` takes it as `definition_digest`, and `POST /api/discovery/approve/{name}` reads it from the query string or a JSON body. Given, the approval applies only a definition that still has that digest, and otherwise is refused with `DiscoveredDefinitionChangedError` (409 on REST) naming the current digest, changing nothing. The 16-character `fingerprint` is unchanged and does not bind. An approval without a digest applies whatever waits under the name, as before, and logs `discovery_approval_not_bound` at WARNING. On REST, a body that is present but not a JSON object, an unknown or misspelt key, a `definition_digest` that is null or not a 64-character lowercase hex digest, and a query and body that disagree answer 400 instead of approving unbound. A pending change is cleared when a scan no longer reports it (the source went back to the running definition, or a healthy source stopped reporting the name), and so are a quarantined change whose source went back and whatever a removed source left waiting. An approval now runs the input validator on the command and the source's own policy, as an automatic registration does, and refuses a definition that fails them or whose source is no longer registered.
