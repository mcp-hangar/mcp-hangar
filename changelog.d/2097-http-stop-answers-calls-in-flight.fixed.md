**core:** a stopping `serve --http` answers the tool calls in flight instead of cutting their streams, and exits within `http.graceful_shutdown_timeout_s`. On SIGTERM sse-starlette closed the stream a pending `tools/call` was answered on, so the client got `peer closed connection` while the call ran on to completion upstream (a retrying client ran it twice), and the process lived as long as its slowest call whatever the bound said. The stop now waits for the MCP requests and batches in flight before it lets the streams close; a 2026-07-28 `subscriptions/listen` stream is not waited for. With the bound unset it waits as long as they take, as before, and the response is delivered. With a bound, once it runs out each `hangar_call` or front-door tool call still running is abandoned and its caller gets a JSON-RPC error with code `-32000` and `data.reason: "shutdown"` on the same stream (`http_shutdown_abandoned_calls`). Other requests still running then (`hangar_start`, `hangar_warm`, a cold `hangar_tools`, a resource read) get no answer: the servers are stopped, their connection ends (`http_shutdown_bound_exceeded`), and the process exits within about the bound plus the component shutdown, ending itself 2 seconds after that if something still holds it (`http_exit_forced`). Stdio is unchanged.
